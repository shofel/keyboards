One state, three transitions

Today the release is a single line: re-pressing an armed one-shot returns to os_up_unqueued, and oneshot_effect() unregisters the modifier on entry to that state. So the tap lands on keydown.

The fix needs a place to sit where the mod is still held but the trigger is down again. os_down_unqueued is the down-side counterpart of the idle state: up/down is where the trigger physically is, queued/unqueued is whether anything is still armed for a future key. Releasing it then moves along one axis only — os_down_unqueued → os_up_unqueued.

Naming

The name was the hard part

The first draft called this state os_down_disarm. That was wrong twice over: a verb among past participles, and an arm/disarm metaphor that appears in the file's prose comments but in none of its identifiers. Pushing on the name is what surfaced everything below — including a version of the change that needs no new state at all.

Struck rows are dominated — os_down_unqueued beats each of them on vocabulary with no compensating win anywhere, so none is the best at anything. os_down_used scores highest on this rubric; it lost on a reweighting, below.

Two ways to add zero states — one broken, one genuinely close. Reuse os_down_unused? Doesn't work. It re-registers the modifier on entry, and its trigger_up returns to os_up_queued — it re-arms instead of disarming, so the tap is never emitted at all. Reuse os_down_used? This one works, and would have reduced the whole change to a single line. The two states have identical outgoing edges on all five events, the same effect mapping and the same mod_held — they are bisimilar, so os_down_unqueued is redundant in the strict sense. It was rejected on legibility: reaching os_down_used when no other key was ever pressed misleads whoever reads the trace next. The extra state is bought for readability, not correctness — worth saying out loud, because it is a real cost. The commit message records it so nobody later assumes the machine needed it.

What flipped it: the rubric above weights minimality at .30 and flexibility at .10. Swap those two — the position you hold if you expect retap-hold to diverge from used-hold later, and if you weight a name a reader can trust — and os_down_unqueued wins 4.20 to 3.45. That was the call made here. The two are within about 1% under any middling weighting, so it is a taste call, not a derivation.

Blast radius

What stays untouched

This is the part that keeps the change cheap. Both FSM helpers absorb the new state correctly without being edited, and nothing downstream enumerates states.

  • oneshot_effect() — unknown states fall through to os_fx_none, which is the right answer here: the modifier is already registered.
  • oneshot_mod_held() — it tests s != os_up_unqueued, so the new state reports held, matching the real registration. The unit test's core invariant holds for free.
  • oneshot.c, introspection.h — no change. The module only drives the table and applies register/unregister.
  • keymap.c — no change. The single reader of one-shot state is mod_ru_suspended() at line 116, and it goes through the predicate.
  • No exhaustive switch over oneshot_state_t exists in live code — grepped across every .c, .h, .md and .py. The one you'll find in docs/superpowers/plans/ is a historical plan document, not compiled.
Ripples

Second-order effects

The state-change event now fires twice read in source

A double-tap walks up_queued → down_unqueued → up_unqueued, so oneshot_process_event runs twice and calls toggle_apply() twice. It early-returns when applied_layer == want (keymap.c:130) — a no-op.

The Russian mask stays up slightly longer derived from the FSM

Russian is masked while a Ctrl/Alt/Gui one-shot holds its mod. That window now extends for however long you hold the second press. It was already held for the whole armed period, so this changes nothing you can feel.

You gain the ability to chord off a retap covered by a test

Previously the second press killed the modifier instantly, leaving nothing to chord with. With os_down_unqueued → os_down_used, holding the re-pressed combo and hitting a key gives you Gui+key and no stray tap on release. Free capability, not a cost — and the retap chord case in the suite pins it down.

The host sees a longer Super hold the one thing to watch

Super is now down for the full duration of the second press. If your desktop does anything on a long Super hold, that's where it would show up. On a quick retap it's invisible.

Combo release produces os_trigger_up assumed, not re-verified

Not a new assumption — the existing hold-to-chord path (os_down_used → os_up_unqueued) already depends on it, and that path works today.

Scope of these claims

Everything above about the state machine was read in source and is now covered by the suite. But the logic is proven off-target only — the left half has not been flashed, so nothing here is a claim about how the retap feels under the fingers. The one thing worth watching for when you do flash it is the longer Super hold spanning the second press.
